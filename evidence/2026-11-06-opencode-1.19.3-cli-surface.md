## 2. Findings that bear directly on locked decisions

### D5 — independent processes: strongly supported

`opencode run` is a self-contained per-task process. One process, one working directory via
`--dir`, one ephemeral local server on a random port, and a raw JSON event stream on stdout via
`--format json`. That maps almost exactly onto "N independent processes, one per worker, each in
its own leased worktree."

**Consequence worth recording: the worker plane may not need `opencode serve` at all.** `serve`
plus `run --attach` plus basic auth is the *shared server* topology that D5 rejected. It exists
and works, but it is not required for the chosen design.

`--port` defaulting to `0` is helpful for concurrency — no port collisions across N workers — but
it means the adapter **must discover the actual bound port from the child's output** rather than
assuming one. That is a hard requirement on the adapter contract (§18 item 1).

### D19 / §8 — usage reporting has a native source

`opencode stats` reports token usage and cost, filterable by model and project. This is the data
source the §8 spend warnings need, and it means the adapter's mandatory per-call usage reporting
is likely satisfiable natively rather than by parsing provider responses.

**Not yet verified:** whether usage appears *per event* in the `--format json` stream (which is
what a live watchdog needs), or only aggregated after the fact via `stats`. This is the single
most important phase-2 question for §8, because a post-hoc aggregate cannot drive a live warning.

### Evidence capture may be native

`opencode export --sanitize` produces redacted session JSON. If the redaction is adequate, this is
a ready-made evidence artefact for §6 phase 4 (proofs attached to the Linear issue) and it already
respects §15's rule that sensitive payloads are not persisted.

**Not yet verified:** what `--sanitize` actually redacts, and whether the exported JSON includes
commands run, exit codes, and file diffs — the specific proofs §13's evidence viewer requires.

### v1's adapter-priority drift was a choice, not a necessity

v1's HOD-1, HOD-2, MVP-3 and Q1 approved **ACP as the preferred first path**. AC-TD-02 and ORC-22
later reprioritised to **server plus pinned SDK** with no superseding record. `opencode acp` is
alive and well in 1.19.3, so nothing forced that change. Recording this because it confirms the
drift was governance failure rather than technical necessity — which is the evidence base for the
binding change-control rule now in §4.

## 3. Security-relevant flags — these must be governed, not merely noted

| Flag | OpenCode's own description | Vestry rule required |
|---|---|---|
| `--auto` | "auto-approve permissions that are not explicitly denied (dangerous!)" | This is OpenCode's own YOLO equivalent, present on both the top level and `run`. **Must never be passed unless the Owner's policy envelope explicitly authorises YOLO mode**, and passing it must be recorded as a governed action. If passed by accident it silently defeats the entire Tier model in §7. |
| `--mdns` | "enable mDNS service discovery (defaults hostname to 0.0.0.0)" | **Hard-deny.** Binding to all interfaces violates §14's loopback-only requirement. Must never be passed. |
| `--cors` | "additional domains to allow for CORS" | Never pass without explicit Owner authorisation. Another exposure vector. |
| `--hostname` | default `127.0.0.1` | Already correct. **Pin it explicitly anyway** so a future OpenCode default change cannot silently widen the bind. |
| `--pure` | "run without external plugins" | Recommended hardening for worker runs. v1's rule stands: plugin entrypoints are trusted local code and are not an isolation boundary. `--pure` removes the question. |
| `-u` / `-p`, `--attach` | basic auth, defaults to `OPENCODE_SERVER_USERNAME` / `OPENCODE_SERVER_PASSWORD` | Belongs to the rejected shared-server topology. If ever used, credentials are injected into the child process environment only, per §15 — never stored. |

The `--auto` finding is the most important item in this file. An orchestrator that spawns workers
with a convenience flag can disable its own governance without any code path deciding to.

## 4. Not yet verified — requires phase 2

Phase 2 requires invoking a model, therefore provider credentials and real token spend. It is
deliberately not done in this record.

1. **Whether abort or kill actually terminates descendants.** The critical §11 question, the
   capability v1 never proved, and the reason D5 exists. Needs a live worker with a spawned child
   process tree, then a kill, then enumeration of what survives.
2. **The actual shape of `--format json` events** — and specifically whether per-event token usage
   is present (see §2 above).
3. **What `export --sanitize` redacts** and whether the export contains the proofs §13 requires.
4. **What `stats` reports and at what granularity** — per session, per project, per model.
5. **Behaviour on mid-run kill** — what state OpenCode leaves behind, and whether `--continue` or
   `--session` can resume it. Directly feeds milestone 1 item 5.
6. **Server-side endpoints** — v1 recorded `/global/health` and `/global/event` SSE, and
   `@opencode-ai/sdk/v2`. None of these are visible from CLI help, so they are neither confirmed
   nor refuted here.
7. **Whether `run` honours a permission policy** without `--auto`, and how it signals a permission
   request back to the supervisor. This determines whether Vestry's Tier model can be enforced
   through OpenCode at all, or must be enforced only by the process boundary.

Item 7 is newly surfaced by this probe and was not in the baseline. It should be added to §18
item 1 when the baseline is next revised.

## 5. Effect on the freeze (D23)

The baseline stays at revision 0.9. Phase 1 confirms D5 and identifies a native usage source for
§8, but it does not resolve the termination question, which is the one that matters most. **Do not
freeze as 1.0 until phase 2 items 1, 2 and 7 are answered.**
