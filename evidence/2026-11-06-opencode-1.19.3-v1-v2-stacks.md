# OpenCode 1.19.3 — the V1/V2 stack split, and an erratum

**Date:** 6 November 2026
**Method:** Read-only inspection of the full source tarball at tag `v1.19.3` of `github.com/anomalyco/opencode`
(commit `e3c4eb2`), extracted locally and grepped. No credentials, **no tokens spent**, no model invoked.
**Local binary:** `opencode --version` → `1.19.3`. Tag matches the installed binary.
Supersedes parts of `2026-11-06-opencode-1.19.3-source-read.md`; the erratum is §1 below.

Triggered by the question *"should we use OpenCode v2?"* — which turns out to have a surprising answer.

---

## 1. ERRATUM against the source-read evidence file

The source-read file traced the abort → tree-kill chain through **`packages/core/src/tool/bash.ts`** and
concluded that the kill is wrapped in `Effect.ignore`, so failure is silent. **That is the wrong module.**
`packages/core/src/tool/bash.ts` is the *V2 core* bash tool, which is not what the live CLI session path
executes. Everything else in that file stands.

The live path is **`packages/opencode/src/tool/shell.ts`** (`ShellTool`), and its kill semantics are
**stronger** than recorded:

```
packages/opencode/src/tool/shell.ts:533-556
  const abort   = Effect.callback(...)            // watches ctx.abort (AbortSignal)
  const timeout = Effect.sleep(input.timeout + 100 millis)
  const exit    = yield* Effect.raceAll([ handle.exitCode, abort, timeout ])
  if (exit.kind === "abort")   yield* handle.kill({ forceKillAfter: "3 seconds" }).pipe(Effect.orDie)
  if (exit.kind === "timeout") yield* handle.kill({ forceKillAfter: "3 seconds" }).pipe(Effect.orDie)
```

`handle` comes from `spawner.spawn(...)` where `spawner = yield* ChildProcessSpawner`
(`shell.ts:20, 342`). `ChildProcessSpawner` is **overridden by OpenCode's own implementation**:
`packages/core/src/cross-spawn-spawner.ts:505` registers
`makeGlobalNode({ service: ChildProcessSpawner, layer, ... })`, and that node is wired into the live session
path at `packages/opencode/src/session/prompt.ts:1618` and the live tool registry at
`packages/opencode/src/tool/registry.ts:445`. So `handle.kill` is CrossSpawnSpawner's override
(`cross-spawn-spawner.ts:427-436`): `killGroup` → `taskkill /pid N /T /F` on Windows,
`process.kill(-pid, sig)` on POSIX, falling back to `killOne`, escalating SIGTERM → SIGKILL after 3 seconds.

**The correction that matters:** the live path pipes the kill through **`Effect.orDie`**, not `Effect.ignore`.
A failed tree kill becomes a propagating defect rather than a silent no-op. The `Effect.ignore` wrapping exists
only in CrossSpawnSpawner's `acquireRelease` *finalizer* (`cross-spawn-spawner.ts:401`), which is a backstop for
scope closure, not the mechanism the shell tool uses.

Two claims in the source-read file therefore need qualification:

| Claim | Status |
| --- | --- |
| Tree kill exists and reaches descendants | **Confirmed, and via the live path** |
| Failure is silent (`Effect.ignore`) | **Wrong for the live path.** `orDie` propagates. Still true of the V2 core bash tool and of the spawner's scope finalizer |
| Windows + already-exited parent gets no cleanup | **Still true** of the finalizer (`cross-spawn-spawner.ts:385-389`), but the live path issues an explicit kill rather than relying on the finalizer |
| Cooperative only — does not survive a hard kill of OpenCode | **Unchanged and still the decisive point.** No finalizer, no `orDie`, no `taskkill` runs if the OpenCode process itself is killed |

The conclusion in §11 of the baseline is unaffected: Vestry must still verify termination independently by Job
Object enumeration. But the reason is now narrower and more honest — not "OpenCode's kill is silent", but
"OpenCode's kill is cooperative, and cooperation is exactly what a hard kill removes."

Also corrected: `killTree` in `packages/core/src/shell.ts:31` — which does the right thing on both platforms —
has **zero callers** in the entire tree at this tag. It is dead code. Any assessment that relied on it, including
the impression given by the source-read file's mention of it, was wrong.

## 2. There is no "OpenCode v2" to choose

The question presumes a switch. There isn't one.

- No `OPENCODE_V2` flag. The complete flag surface is `packages/core/src/flag/flag.ts`; it contains no V1/V2
  mode toggle.
- No separate binary, no separate npm package, no `--v2` flag on any command.
- `opencode debug v2` exists but is only a catalog dumper — it prints available providers and default/small
  models as JSON (`packages/opencode/src/cli/cmd/debug/v2.ts`). It does not enable anything.
- The installed version is `1.19.3`; the version line never became "2.x".

"V2" in this codebase is an **in-flight internal rearchitecture**, not a product version. Both stacks ship in the
same binary at the same time.

## 3. What the two stacks actually are

**V1 stack — `packages/opencode/src/`.** This is the live path. `packages/opencode/src/session/tools.ts` resolves
the tools the model actually receives from `@/tool/registry` = `packages/opencode/src/tool/registry.ts`, which
registers `ShellTool`, `TaskTool`, `PlanExitTool`, `QuestionTool`, `EditTool`, `GlobTool`, `GrepTool`, `ReadTool`,
`TodoWriteTool`, `WebFetchTool`, `WriteTool`, `InvalidTool`, `SkillTool`, `WebSearchTool`, `LspTool`, plus MCP and
plugin tools. It uses `Permission` from `@/permission` (V1).

**V2 core — `packages/core/src/`.** A parallel, partially complete port. `packages/core/src/tool/builtins.ts`
registers `BashTool`, `ApplyPatchTool`, `EditTool`, `GlobTool`, `GrepTool`, `QuestionTool`, `ReadTool`,
`SkillTool`, `TodoWriteTool`, `WebFetchTool`, `WebSearchTool`, `WriteTool` — using `PermissionV2`. It is mounted
only through `packages/core/src/location-services.ts:35`, whose consumers are `debug v2`, the file handlers and
the pty handler — **not** the session prompt path.

`packages/core/src/v1/` (20 files) is a compatibility shim, mostly config sub-modules plus `permission.ts` and
`session.ts`, with `migrate.ts` translating V1 config into V2 shape. The CLI still speaks the V1 permission shape:
`run.ts` builds a `PermissionV1.Ruleset` and passes it to `session.create`.

Two permission schemas coexist and are not the same shape:

| | shape |
| --- | --- |
| V1 config (`packages/core/src/v1/config/permission.ts`) | `{ <tool>: "ask"\|"allow"\|"deny" \| { <pattern>: action } }` |
| V2 runtime (`packages/schema/src/permission.ts:54-61`) | `Rule { action, resource, effect: "allow"\|"deny"\|"ask" }` |

## 4. The V2 core's parity debt lands exactly where Vestry is most exposed

`packages/core/src/tool/bash.ts:62-77` is a block of twelve TODOs the upstream authors wrote themselves. The
ones that matter here, quoted:

- `// TODO: Port tree-sitter bash / PowerShell parser-based approval reduction.`
- `// TODO: Port BashArity reusable command-prefix approvals.`
- `// TODO: Restore PowerShell and cmd-specific invocation/path handling on Windows.`
- `// TODO: Persist background job status and define restart recovery before exposing remote observation.`
- `// TODO: Re-add model-facing background launch only with owner-bound get/wait/cancel tools and completion delivery.`
- `// TODO: Revisit process-group cleanup and platform coverage with shell-specific tests if current AppProcess semantics do not fully cover it.`

Every one of those is a capability the **V1 stack has and V2 does not yet**:

- **tree-sitter command parsing** — live in V1 (`shell.ts:622`, `web-tree-sitter`), absent from V2 core.
- **`BashArity`** (`packages/opencode/src/permission/arity.ts`) — a command-prefix arity dictionary that reduces a
  raw shell command to its "human-understandable command" so an approval for `git checkout` covers
  `git checkout -b foo`. Live in V1, not ported.
- **Windows PowerShell / cmd handling** — live in V1: `shell.ts:293-300` invokes PowerShell as
  `-NoLogo -NoProfile -NonInteractive -Command` with `detached: false`, and `packages/core/src/shell.ts` resolves
  Git Bash on Windows. V2 core's `bash.ts` says this is not restored.
- **`task` (subagent spawning), `plan`, `lsp`, `code-mode`** — registered in V1, **absent from V2 core builtins**.
- **background job persistence and restart recovery** — not defined in V2.

Vestry is Windows-first (D3) and its two hardest requirements are §11 descendant termination and restart
reconciliation (§19 milestone items 4 and 5). The unfinished stack is the one that has not yet restored Windows
shell handling or defined restart recovery.

**So: no.** Not even if there were a switch. Binding Vestry to the V2 core today would mean accepting the loss of
Windows-specific shell invocation, coarser approval granularity, no subagent tool, and an undefined restart
story — in exchange for nothing Vestry needs.

## 5. The reframe: Vestry should bind to neither stack

The V1/V2 split is internal churn. It is precisely what a version bump is *expected* to rearrange, and it is
already rearranging: upstream shipped `1.19.5` during this read, and the migration is unfinished at `1.19.3`.

What a version bump is expected to *preserve* is the external contract. That is what the adapter should bind to:

**CLI surface** — `run`, `serve`, `export`, `stats`, `--format json`, `--port`, `--hostname`, `--pure`, `--dir`.

**HTTP/SSE surface** — `/global/health`, `/global/event`, `GET /event`, `/session/:id/abort`,
`/session/:id/message`, `/session/:id/permissions/:permissionID`.

**Config and environment contract** — and this is where the read paid for itself. From
`packages/core/src/flag/flag.ts`:

| variable | why it matters to Vestry |
| --- | --- |
| `OPENCODE_PERMISSION` | **A complete per-dispatch permission policy as inline JSON**, deep-merged into config at `packages/opencode/src/config/config.ts:559-563`. V1 shape supports per-tool patterns (`bash: {"git *": "allow", "*": "ask"}`), and key order is preserved for precedence. This is a materially better Tier-enforcement path than the per-agent ruleset recorded in §7: no files written into the leased worktree, no agent definition to manage, distinct policy per attempt. Invalid JSON is logged and skipped — so the adapter must confirm the policy actually took effect rather than assume it |
| `OPENCODE_DISABLE_PROJECT_CONFIG` | Stops the **target repository's own** `opencode.json` from being read into the worker. Without it, a repo can alter the worker's model, permissions and plugins — a direct R8 prompt-injection and policy-escape vector. Should be set on every dispatch |
| `OPENCODE_CONFIG_CONTENT` / `OPENCODE_CONFIG` / `OPENCODE_CONFIG_DIR` | Inject worker config without writing into the worktree |
| `OPENCODE_DB` | Relocate the session store. Lets each worker get its own throwaway database, which is the answer to the observed 2.25 GB single-user growth |
| `OPENCODE_DISABLE_AUTOUPDATE` | Closes the version-drift vector, alongside never calling `POST /global/upgrade` |
| `OPENCODE_PURE` | Env equivalent of `--pure`; no external plugins loaded |
| `OTEL_EXPORTER_OTLP_ENDPOINT` / `_HEADERS` | **OpenCode already exports OpenTelemetry natively** — `packages/core/src/observability/otlp.ts` uses `@opentelemetry/exporter-trace-otlp-http`'s `OTLPTraceExporter`. Directly relevant to D19: worker-side traces may need no adapter instrumentation at all, and the loopback-only OTLP posture already decided for Vestry's own traces applies unchanged |
| `OPENCODE_SERVER_PASSWORD` / `_USERNAME` | Basic auth for `serve`; both currently unset on this machine, so auth is off unless Vestry sets it |
| `OPENCODE_GIT_BASH_PATH` | Windows Git Bash override |
| `OPENCODE_EXPERIMENTAL_WORKSPACES` | Workspaces are **experimental** and off by default; not a substitute for Vestry's own worktree leases |

Three of these change baseline content: `OPENCODE_PERMISSION` improves the §7 enforcement story,
`OPENCODE_DISABLE_PROJECT_CONFIG` is a new §15 requirement, and native OTLP export narrows §18 item 9.

## 6. Answer to the question as asked

**No — and the question dissolves on inspection.** There is no v2 to opt into; `1.19.3` runs the V1 stack for
everything Vestry would touch, with the V2 core mounted only for debug and file/pty handlers. If a switch did
exist, V2 would be the wrong choice today, because its own authors list unported Windows shell handling,
unported approval granularity, no `task` tool, and undefined restart recovery — the exact areas §11 and §19
items 4 and 5 depend on.

The durable decision is not *which stack* but *which layer*: bind the adapter to the CLI, HTTP/SSE and
config/env contract, never to `packages/core` or `packages/opencode` internals. Then the V1→V2 migration
completing upstream is a non-event, and R5's pin-and-fail-closed mitigation is sufficient.

**Still unverified without a live probe:** that `OPENCODE_PERMISSION` is honoured by `opencode run` in practice;
that the tree kill actually reaps descendants on this Windows machine; and whether the V1 `ShellTool` or the V2
`BashTool` handles a given command under a real dispatch. Reading source establishes which module is wired; only
execution establishes which one fires.
