## 1. Does abort actually terminate descendants? — Mostly yes, cooperatively. Not a containment boundary.

This is the §11 question, the capability v1 never proved, and the reason D5 exists. The full chain, verified
file by file:

```
POST /session/:sessionID/abort
  packages/opencode/src/server/routes/instance/httpapi/handlers/session.ts:232
    → promptSvc.cancel(sessionID)
  packages/opencode/src/session/prompt.ts:152  SessionPrompt.cancel
    → state.cancel(sessionID)
  packages/opencode/src/session/run-state.ts:77  SessionRunState.cancel
    → cancelBackgroundJobs(background, sessionID)   [first]
    → existing.cancel                               [then]
  packages/opencode/src/effect/runner.ts:171-183  Runner.cancel
    → Fiber.interrupt(st.run.fiber)                 [awaits, does not fork]
  packages/opencode/src/session/prompt.ts:815-827
    → Effect.onInterrupt(() => controller.abort())  [AbortController]
  packages/core/src/process.ts:189-195  AppProcess.run
    → Effect.raceFirst(waitForAbort(signal))        [scope closes on abort]
  packages/core/src/cross-spawn-spawner.ts:373-403  acquireRelease finalizer
    → killGroup, escalating to SIGKILL
```

`killGroup` (`cross-spawn-spawner.ts:292-312`) is a genuine tree kill:

- **Windows:** `taskkill /pid <pid> /T /F` — `/T` walks the child tree, `/F` forces.
- **POSIX:** `process.kill(-proc.pid, signal)` — negative PID, i.e. the whole process group.
- Escalation: `killSignal ?? "SIGTERM"`, then after `forceKillAfter` → `"SIGKILL"`
  (`cross-spawn-spawner.ts:391-401`). The bash tool sets `forceKillAfter: Duration.seconds(3)`
  (`packages/core/src/tool/bash.ts:163`).
- Fallback: if `killGroup` fails, it falls back to `killOne` = `proc.kill(signal)` — single process only
  (`cross-spawn-spawner.ts:392`).

`cancelBackgroundJobs` (`run-state.ts:111-143`) does a **transitive closure walk**, not a flat list: it seeds a
pending set with the session ID, cancels every `status === "running"` job whose `id`, `metadata.sessionId` or
`metadata.parentSessionId` is in the set, adds each cancelled job's ID and session to the set, and loops until
no new match. Subagent sessions and nested background jobs are therefore reached.

`Fiber.interrupt` (not `interruptAsFork`) means `cancel` blocks until interruption and finalizers complete, so
`/abort` returning `true` is stronger than a bare ACK.

### Four gaps that Vestry must not paper over

1. **The tree kill is wrapped in `Effect.ignore`** (`cross-spawn-spawner.ts:401`). A failed `taskkill` is
   swallowed. `Fiber.interrupt` completes regardless. So `/abort` → `true` still means *"we attempted the tree
   kill and stopped waiting"*, not *"descendants are provably gone"*. v1's rule — abort ACK ≠ descendant
   termination — survives, in a narrower form.
2. **Windows + already-exited = zero cleanup.** The finalizer's `done` branch returns `Effect.void` immediately
   on win32 (`cross-spawn-spawner.ts:385-389`). If the shell wrapper exited but left a detached grandchild
   (`start`, `npm run dev`, a service, docker), nothing reaps it. `taskkill /T` walks the PID tree, and the tree
   link dies with the intermediate parent.
3. **All of this is cooperative.** It requires the OpenCode process to be alive and running its Effect runtime.
   If Vestry hard-kills OpenCode — which is exactly what the D15 watchdog and the process-console kill button
   do — **no finalizer runs at all** and every descendant is orphaned. This is the decisive argument for D3's
   Job Object: a `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` job kills the whole tree whether or not OpenCode
   cooperated. OpenCode's tree kill is best-effort-at-graceful-shutdown; it is not a containment boundary.
4. **Upstream says the coverage is unverified.** `packages/core/src/tool/bash.ts:75` carries the literal TODO
   *"Revisit process-group cleanup and platform coverage with shell-specific tests if current AppProcess
   semantics do not fully cover it."*

Also from `bash.ts:72-74`: background job status is **not persisted**, restart recovery is **not defined**, and
background-job observation is **not exposed**. A process a worker launches in the background is invisible to
Vestry and unrecoverable across a restart.

`detached` defaults to `process.platform !== "win32"` (`cross-spawn-spawner.ts:378`; bash tool sets it
explicitly the same way at `bash.ts:162`). On Windows there is no separate process group and no job object, so
containment rests entirely on the PID-tree walk being intact.

**Live-probe status:** still required. Reading source proves intent, not behaviour on this machine. Item 1 of
the freeze condition is answered *on paper* and must be confirmed empirically before Baseline 1.0.

## 2. `--format json` event shape — confirmed, and it does **not** carry usage

`packages/opencode/src/cli/cmd/run.ts:668-681`. NDJSON, one object per line:

```json
{ "type": "<string>", "timestamp": <epoch-ms>, "sessionID": "<id>", ...data }
```

The complete set of emitted types (`run.ts:715, 736, 740, 744, 757, 779, 845, 862`):

| type | payload | source event |
| --- | --- | --- |
| `tool_use` | `{ part }` | `message.part.updated`, tool part completed/errored |
| `step_start` | `{ part }` | part type `step-start` |
| `step_finish` | `{ part }` | part type `step-finish` |
| `text` | `{ part }` | part type `text` with `time.end` |
| `reasoning` | `{ part }` | part type `reasoning`, only when `--thinking` |
| `error` | `{ error }` | `session.error`, or a failed `prompt`/`command` call |

There is **no `usage` event, no `message.updated` event, and no `done`/`finish`/`result` event.** The loop
simply `break`s on `session.status == idle` for the session (`run.ts:781-788`) and the process exits, setting
`process.exitCode = 1` if any error was seen. Completion is inferred from process exit, not announced.

`message.updated` *is* consumed (`run.ts:698-709`) but only to print the `> agent · modelID` header, and only
when `args.format !== "json"`.

### Where usage actually lives

`packages/schema/src/session-message.ts:165-189`, the `Session.Message.Assistant` schema:

```
agent:   string
model:   Model.Ref                // providerID + modelID
finish:  string?
cost:    Finite?
tokens:  { input, output, reasoning, cache: { read, write } }   // all Finite
time:    { created, completed? }  // ms since epoch → per-call duration
error:   UnknownError?
```

This is exactly the per-call model / token count / duration data §8 requires — and it is **rolled up onto the
session row** by `packages/core/src/database/migration/20260510033149_session_usage.ts`, which adds
`cost`, `tokens_input`, `tokens_output`, `tokens_reasoning`, `tokens_cache_read`, `tokens_cache_write` to
`session`, backfilled from `json_extract(message.data, '$.cost')` and `'$.tokens.*'`.

**Consequence, and it is a real design constraint.** Live per-call usage is available on the assistant message,
which arrives over the **server event stream** (`GET /event`, SSE) or the session database — **not** over
`opencode run --format json`. So:

- `run --format json` alone can support **post-hoc** spend accounting (read the session row or `opencode stats`
  after exit) but **not** the live warnings §8 and D16 require.
- Live spend warnings need either (a) one `opencode serve --port 0 --hostname 127.0.0.1` **per worker**, with
  Vestry subscribed to that instance's `/event` stream — which preserves D5's "N independent processes" because
  each server is still one worker's own process inside Vestry's Job Object; or (b) polling the session store.

This reshapes §18 item 1. The D5 decision (independent processes, not one shared server) is **unaffected and
in fact reinforced** — what changes is that the independent process is probably `serve`, not `run`. The rejected
topology was *one shared server with N sessions*; N private servers is a different thing.

## 3. Does `run` honour a permission policy without `--auto`? — Yes, but the policy lives on the agent, and `ask` means reject

Answered definitively.

**Headless `run` has exactly two behaviours, and neither is "ask a human".** `run.ts:791-811`:

```
if (auto)  → client.permission.reply({ requestID, reply: "once" })
else       → print "permission requested: <p> (<patterns>); auto-rejecting"
             client.permission.reply({ requestID, reply: "reject" })
```

Without `--auto`, every permission request is **auto-rejected**. It does not block, does not wait, and does not
signal the supervisor beyond that stdout line (which `--format json` does not even emit — it is a `UI.println`,
not an `emit`). With `--auto`, every request not explicitly denied is **approved once**. There is no third mode.

`--auto` has two **hidden** aliases that phase 1's `--help` did not show (`run.ts:248-257`,
`run.ts:275`): `--yolo` and `--dangerously-skip-permissions`. All three are OR'd into one `auto` boolean. Any
governed-action check on the flag must match all three spellings.

**The real policy hook is the agent's permission ruleset.** The CLI builds only a fixed three-rule ruleset for
non-interactive mode (`run.ts:431-448`) denying `question`, `plan_enter` and `plan_exit`, and passes it to
`session.create({ permission: [...rules] })`. Arbitrary rules cannot be passed on the command line.

Evaluation is in `packages/core/src/permission.ts`:

- `configured(sessionID, agentID)` (line 137-145) resolves the ruleset from **`agent.permissions`**. If no agent
  resolves, it returns `missingAgentPermissions = [{ action: "*", resource: "*", effect: "deny" }]` (line 15) —
  a **fail-closed default**, which is the right shape.
- `Effect` is `"allow" | "deny" | "ask"`; `Rule` is `{ action, resource, effect }`
  (`packages/schema/src/permission.ts:54-61`). Agents carry `permissions: Permission.Ruleset` plus
  `mode: "subagent" | "primary" | "all"` and `model: Model.Ref` (`packages/schema/src/agent.ts:22-30`).
- `evaluateInput` (line 155-162): if any resource is `deny` → deny immediately. Otherwise merge agent rules with
  `savedRules()`, and `deny > ask > allow`.
- `assert` (line 198-206): `deny` → fail; `allow` → proceed; `ask` → create a pending request and block on a
  `Deferred`. In headless `run` that block is resolved by the auto-reject above.

**So the Tier model is encodable — through a per-dispatch agent definition, not through CLI flags.** Vestry
generates an OpenCode agent whose `permissions` ruleset allows Tier A actions, denies hard-denied and Tier C
actions, and marks everything else `ask` — knowing `ask` in headless mode resolves to *reject*, which is the
safe direction. A rejected Tier B action then surfaces as a failed tool call, and Vestry raises an attention
item and re-dispatches with an amended ruleset. Escalation is a Vestry-level loop, never an OpenCode-level wait.

**One leak to close.** `savedRules()` (`permission.ts:131-135`) reads `PermissionSaved` for the project and maps
every saved entry to `effect: "allow"`. Saved approvals therefore **persist per project and auto-allow in all
later sessions**. A single `"always"` reply permanently widens the envelope for that project directory. Mitigation:
Vestry must never permit an `"always"` reply (headless `run` already only ever sends `"once"`), and should isolate
or reset the saved-permission store per task. Flagged as a new §15 requirement.

Note `packages/core/src/tool/bash.ts:66-67` TODOs: tree-sitter bash/PowerShell parser-based approval reduction
and `BashArity` reusable command-prefix approvals are **not yet ported to V2**. Bash approval granularity today is
the raw command string as the resource (`bash.ts:142-149`).

## 4. Server surface — confirmed, and more dangerous than v1 recorded

`packages/opencode/src/server/routes/instance/httpapi/groups/global.ts:68-74`:

```
GET   /global/health    → { healthy: true, version }
GET   /global/event     → SSE, GlobalEvent { directory, project?, workspace?, payload }
GET   /global/config    → ConfigV1.Info
PATCH /global/config    → update global config
POST  /global/dispose   → dispose all instances, release all resources
POST  /global/upgrade   → { target: semver } — upgrades the opencode binary
```

`groups/event.ts:7-9`: `GET /event` — the instance-scoped SSE stream, `text/event-stream`, behind
`InstanceContextMiddleware`, `WorkspaceRoutingMiddleware` and `Authorization`.

`groups/control.ts:31-34`:

```
PUT    /auth/:providerID   → set provider credentials
DELETE /auth/:providerID   → remove provider credentials
POST   /log                → write a log entry
```

v1's recorded `/global/health` and `/global/event` are **confirmed present** at 1.19.3.

**Security consequence.** A running `opencode serve` exposes, on loopback HTTP, the ability to **replace the
binary** (`/global/upgrade`), **rewrite global config** (`PATCH /global/config`), **dispose every instance**
(`/global/dispose`), and **inject or delete provider credentials** (`PUT`/`DELETE /auth/:providerID`). Any local
process that can reach that port can do this. `run.ts` imports `ServerAuth` and `--password`/`--username`
default to `OPENCODE_SERVER_PASSWORD` / `OPENCODE_SERVER_USERNAME` — both currently unset on this machine, so
basic auth would be off unless explicitly configured.

This does not by itself refute per-worker `serve` (option 2a above), but it makes three things mandatory if
Vestry takes that route: an ephemeral `--port 0` with the bound port discovered from child output, `--hostname
127.0.0.1` pinned explicitly, and a per-worker `OPENCODE_SERVER_PASSWORD` generated by Vestry, injected only
into that worker's environment, and never logged or stored. `--mdns` stays hard-denied (it rebinds the hostname
to `0.0.0.0`).

## 5. Version drift observed while reading

Installed binary is `1.19.3`; upstream has already shipped `1.19.5`. Everything in this file is pinned to the
`v1.19.3` tag and must be re-verified against whatever version the adapter actually pins. This is the concrete
form of R5, and it is why §14 requires adapters to discover, report and pin versions and fail closed on
mismatch. `POST /global/upgrade` means an OpenCode instance can change its own version at runtime — Vestry must
never call it, and should treat an unexpected version change as a fail-closed condition.
