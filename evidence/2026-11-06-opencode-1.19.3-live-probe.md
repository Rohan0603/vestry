`opencode auth list` showed the Owner already holds credentials for **OpenAI oauth**, **OpenCode Go api** and **OpenRouter api** in `~/.local/share/opencode/auth.json`, plus **Google `GEMINI_API_KEY`** in the environment. No credential was requested from or supplied by the Owner for this probe.

**P0.1** `opencode run --model openrouter/openrouter/free "Reply with exactly one word: PONG"` → exit 0, output `PONG`, banner reporting `build · openrouter/free`.

**P0.1b — `OPENCODE_DB` works, and this is the finding that matters for §18 item 10.** Setting `OPENCODE_DB` to a Windows-style absolute path (`C:/Users/.../db/opencode.db`) created a fresh store there and left the Owner's real `~/.local/share/opencode/opencode.db` (2,257,473,536 bytes) with an unchanged mtime. **`auth.json` is a separate file from the database, so a relocated store still authenticates** — which is exactly what Vestry needs for per-worker throwaway databases.

Two caveats, both my errors rather than OpenCode's, recorded so they are not repeated:

- The first attempt set the variable as `WOPENCODE_DB` (typo) and silently wrote to the real 2.25 GB store. Detected by observing that the probe `db/` directory stayed empty while the real store's mtime advanced. Corrected and re-run.
- The value must be a **Windows** absolute path. A Git-Bash-style `/c/Users/...` would satisfy Node's `isAbsolute` on win32 and be handed to SQLite as `C:\c\Users\...`. Vestry must construct these paths as Windows paths.

Measured growth for retention modelling: **983,040 bytes for 18 sessions and 54 messages** — roughly 55 KB per session and 18 KB per message. The Owner's 2.25 GB store therefore represents on the order of 40,000 sessions. Extrapolating to three concurrent autonomous workers is a real disk-pressure question and Vestry can now control it per worker.

**P0.2 — `--format json`, and the first reversal.** Three lines for a one-word reply:

```json
{"type":"step_start","timestamp":1793913769894,"sessionID":"ses_e52683f74ffelHjlBWKl8vou6p","part":{...,"type":"step-start"}}
{"type":"text","timestamp":1793913770011,"sessionID":"...","part":{...,"type":"text","text":"PONG","time":{"start":...,"end":...}}}
```

`step_finish` **carries `tokens` and `cost`.** The source read concluded usage was absent from `run --format json` because there is no separate usage event and no completion event; that was correct as far as it went and wrong in its consequence. Usage is embedded in the `step_finish` part, per step, including all five token counters and a cache breakdown.

Two structural notes: the outer `type` uses underscores (`step_finish`) while `part.type` uses hyphens (`step-finish`) — a parser must not conflate them. And each part carries a `snapshot` SHA, which is a free provenance handle Vestry can record without extra calls.

Also visible: **23,926 input tokens for a one-word reply.** That is the system prompt plus tool schemas, and it is the floor on every dispatch. Later calls in the same session showed `cache.read` of 21,920 against `input` of 2,018, so prompt caching does engage across steps. Any Vestry cost model must start from ~20–24K input tokens per call, not from the size of the task prompt.

**P0.3 — the free router can call tools.** Prompted to create `pong.txt`, the run reported `← Write pong.txt` and the file was verified on disk containing `PONG`. Verified by filesystem inspection, not by trusting the transcript. This was the gate on P1, P2, P3 and P7, and it opened.

## 2. P1 — permission enforcement, and the second reversal

### 2.1 The default is allow-everything

**P1a** ran `echo VESTRY_BASH_OK` with **no `--auto` and no `OPENCODE_PERMISSION`**. It executed. The command ran and returned its output.

The cause is in `packages/opencode/src/agent/agent.ts:119-136`, the `defaults` ruleset merged into every agent:

```ts
const defaults = Permission.fromConfig({
  "*": "allow",
  doom_loop: "ask",
  external_directory: { "*": "ask", ...whitelistedDirs → "allow" },
  question: "deny",
  plan_enter: "deny",
  plan_exit: "deny",
  read: { "*": "allow", "*.env": "ask", "*.env.*": "ask", "*.env.example": "allow" },
})
```

`"*": "allow"`. The `build` agent then merges `defaults`, a small `{question, plan_enter}` override, and the user's config — in that order, so user config wins but the floor is allow-all.

Two things follow, and both belong in the baseline:

1. **There is no safe default.** Headless `opencode run` with zero configuration will execute arbitrary shell commands. The source-read statement that headless mode "auto-rejects every request" is true only of requests that get raised, and under default-allow almost none do. Vestry must set an explicit policy on **every** dispatch, and a dispatch that reaches the child without one is a defect.
2. **Some protection is free.** `read` gates `*.env` and `*.env.*` behind `ask` (which headless resolves to reject) while allowing `*.env.example`, and `external_directory` gates writes outside the project. Vestry inherits both and should not weaken them.

The Owner's own `~/.config/opencode/opencode.json` sets all thirteen permission keys to `"allow"` — which, given the built-in default, is redundant. It also loads two global plugins, `@dietrichgebert/ponytail` and `superpowers@git+https://github.com/obra/superpowers.git`, and their instructions demonstrably reach the worker: in the P4 run the model's visible reasoning began *"The user has provided instructions about using skills in this system… Before entering plan mode, I should invoke the brainstorming skill first."* Nothing in the probe repository asked for that. See §7.

### 2.2 `OPENCODE_PERMISSION` is honoured, and it overrides global config

| Test | Policy | Command | Result |
| -- | -- | -- | -- |
| P1b | `{"bash":{"*":"deny"}}` | `echo …` | Tool **removed from the model's tool list**. Error: `Model tried to call unavailable tool 'shell'. Available tools: edit, glob, grep, invalid, read, skill, task, todowrite, webfetch, write` |
| P1c | `{"bash":{"echo *":"allow","*":"deny"}}` | `echo …` | Tool **removed** — the trailing `*` deny won |
| P1f | `{"bash":{"echo *":"allow","*":"ask"}}` | `echo …` | Tool present; request raised and **auto-rejected**: `! permission requested: bash (echo VESTRY_F_OK); auto-rejecting` |
| P1g | same as P1f | `cmd /c ver` | Same rejection path |
| P1h | `{"bash":{"*":"ask","echo *":"allow"}}` | `echo …` | **Ran, no prompt** |
| P1j | `{"bash":{"*":"deny","echo *":"allow"}}` | `echo …` | **Ran, no prompt** |
| P1i | `{"bash":"allow"}` (plain string) | `cmd /c ver` | **Ran, no prompt** |

Three rules fall out, and they are directly actionable for the adapter contract:

**Last matching key wins.** P1c and P1j carry the same two rules in opposite order and behave oppositely. This is consistent with `propertyOrder: "original"` in the V1 permission schema. An allow-list is therefore expressible, but only in one order: wildcard first, specifics after.

```json
{"bash": {"*": "ask", "git status": "allow", "npm test": "allow", "cargo test": "allow"}}
```

Written the other way round it silently denies everything. This is a footgun worth a conformance test of its own, because the failure is silent and looks like a model refusing to cooperate.

**`deny` and `ask` are observably different, and `ask` is the better default for Vestry.** `deny` removes the tool from the model's tool list entirely — the model then hallucinates alternative tool names (it tried `shell` in P1b and `bash` in P1c) and produces an `invalid` tool event. `ask` keeps the tool exposed and produces a **named, auditable rejection** carrying the exact command: `permission requested: bash (echo VESTRY_F_OK); auto-rejecting`. Vestry wants that string in its audit record; it is the difference between "the worker was denied X" and "the worker never had X". `invalid` tool usage is itself counted — `stats` reported `invalid 2 (12.5%)` after the deny tests.

**Invalid JSON fails open, silently.** P1e set `OPENCODE_PERMISSION='{invalid json'`. Exit 0, no warning on stdout or stderr, and `echo VESTRY_INVALIDJSON` ran. This confirms the `config.ts:559-563` reading empirically: the parse error is logged via `Effect.logWarning` at a level that does not reach the CLI's output, and the merge is skipped, leaving default-allow in force.

Combined with §2.1 this is the worst failure mode in the whole probe: **a malformed policy string degrades to allow-everything, invisibly.** Vestry cannot treat "I set `OPENCODE_PERMISSION`" as "the policy is in force". The adapter must prove it — a canary dispatch under a deny-all policy, asserting the tool is absent, before any real work — and must validate the JSON itself before spawning.

### 2.3 No flag suppresses global config

P1k set `OPENCODE_PURE=1`; P1l set `OPENCODE_CONFIG_DIR` to an empty directory. Both still ran bash with no prompt. Source explains all three cases:

- `OPENCODE_CONFIG_DIR` is **additive** — `config/paths.ts:39` appends it to a search list that already begins with `Global.Path.config`. It redirects where global config is read from (`global.ts:64`) but the effective result here was indistinguishable because of the built-in default-allow, not because the redirect failed.
- `OPENCODE_PURE` reaches only `plugin/tui/runtime.ts:1089` — it suppresses **plugin origins in the TUI**, not headless config loading.
- `OPENCODE_CONFIG_CONTENT` **merges**; `config.ts:264` uses those flags only to decide whether to *seed* a default global config file, never whether to load one.

So `OPENCODE_DISABLE_PROJECT_CONFIG` does what it says — it removes the `.opencode` directories walked up from the working directory (`paths.ts:27`, `instruction.ts:81,123`, `instruction-context.ts:48`) — and it is still worth setting on every dispatch. But **no flag in 1.19.3 removes the Owner's global config or global plugins from a worker's prompt.** Isolation has to come from `OPENCODE_PERMISSION` overriding the merged result, plus `OPENCODE_DB` isolating state, plus accepting that plugin-injected instructions are part of the worker's input. §7 of the baseline claimed `OPENCODE_DISABLE_PROJECT_CONFIG` closed the repo-driven policy escape; it closes the *project*-driven one and leaves the *global* one open.

## 3. P2b — a hard kill orphans descendants (proven, twice)

Setup: `OPENCODE_PERMISSION='{"bash":"allow"}'`, prompt `Run the shell command: sleep 313`. The tree that formed, read from `Win32_Process`:

```
timeout.exe 15244
└─ sh.exe 21668          (npm shim: /c/Users/ponna/AppData/Roaming/npm/opencode)
   └─ opencode.exe 28940  C:\Users\ponna\AppData\Roaming\npm\node_modules\opencode-ai\bin\opencode.exe
      └─ bash.exe 17036   "C:\Program Files\Git\usr\bin\bash.exe" -c "sleep 313"
         └─ sleep.exe 10416
```

Killed **only** PID 28940, with `Stop-Process -Force` — no `/T`, no cooperation, no signal handling. Eight seconds later:

```
opencode.exe 28940 : gone (killed)
bash.exe     17036 : gone
sleep.exe    10416 : ALIVE  ->  "C:\Program Files\Git\usr\bin\sleep.exe" 313
```

`sleep.exe` survived with a `ParentProcessId` pointing at a process that no longer existed. It would have run for another five minutes.

**Reproduced independently in P3:** hard-killing `opencode.exe` mid-turn left `sleep.exe` 20784 alive under dead parent 12020.

This is the §11 invariant, empirically: **an abort ACK is not descendant termination, and a hard kill runs no finalizer at all.** The source read predicted exactly this — the whole `taskkill /T /F` chain is cooperative, so nothing executes it when the process is killed outright. Two consequences for the design:

1. Vestry's Job Object is not a refinement, it is the mechanism. Killing the worker process is insufficient by construction, and the watchdog's kill path will orphan whatever the worker had spawned.
2. Note also that `opencode.exe` is a **native binary**, not a Node script — so "find the node process and kill it" is not a strategy that would have worked here either, and the npm shim adds two extra process levels above it.

Both orphans were enumerated and killed during the probe; a final `Win32_Process` filter for `sleep.exe` returned `none`.

## 4. P3 — resume after a mid-run kill reconciles

Started a run with `--format json`, captured `sessionID = ses_e52574f03ffei3WjaGyz5UwtyW` from the stream, waited for the tool call to fire, hard-killed `opencode.exe` mid-turn, then resumed:

```
opencode run --session ses_e52574f03ffei3WjaGyz5UwtyW --model openrouter/openrouter/free --format json \
  "What shell command did you run earlier in this session? Answer with just the command."
```

→ exit 0, `"text":"sleep 45"`.

The interrupted turn's tool call had been persisted, the resumed session had coherent history, and there was **no duplication and no silent replay** of the command. This is good news for milestone item 5 and for §12: `--session <id>` is a usable reconciliation handle, and the session store survives an unclean worker death.

The limit of what this shows: one short turn, one tool, killed once. It does not establish behaviour when the killed turn was mid-write, mid-commit, or several tools deep — that is milestone 1's job, with Vestry's own lease and base-SHA machinery around it.

`opencode session list` also works against the relocated store and returns `Session ID / Title / Updated`, with titles auto-generated from the first prompt.

## 5. P4 — `export --sanitize` is adequate

Planted the marker `VESTRY-FAKE-SECRET-9f3k2m` into a session (the model repeated it three times; it also landed in the auto-generated session title).

| | bytes | marker occurrences |
| -- | -- | -- |
| `opencode export <sid>` | 16,448 | **32** |
| `opencode export <sid> --sanitize` | 7,814 | **0** |

Sanitisation replaces values with typed, self-describing placeholders that preserve structure and traceability:

```
raw:       "directory": "C:\\Users\\ponna\\AppData\\Local\\Temp\\vestry-probe-2026-11-06\\repo"
sanitized: "directory": "[redacted:session-directory:ses_e525ba84effeAs2V3NbTuBte2I]"
raw:       "title": "Repeating token VESTRY-FAKE-SECRET-9f3k2m 3 times"
sanitized: "title": "[redacted:session-title:ses_e525ba84effeAs2V3NbTuBte2I]"
```

Session id, slug, project id and agent name are retained, so a sanitised export is still joinable to Vestry's own records. **This is usable as an evidence-capture path under §15**, with one caveat that the probe did not test: the marker was planted in the transcript and the title, not in a file path, a tool argument, an environment dump or a diff. Redaction of *those* is unverified, and a diff or a bash argument is exactly where a real secret would appear. Vestry should treat `--sanitize` as a first pass and still apply its own redaction before anything reaches Linear.

## 7. P7 — the V1 stack fires, and the tool name cannot tell you

The runtime emitted `"tool":"bash"`. That looked like an answer and is not one: `packages/opencode/src/tool/shell/id.ts` sets

```ts
// Keep the exposed tool ID and permission key as "bash" for compatibility with
// existing plugins, users, and saved permissions. Rename with opencode 2.0.
export const ToolID = "bash"
```

while the V2 core's `packages/core/src/tool/bash.ts:18` sets `export const name = "bash"`. **Both stacks expose the same tool name**, so the name is not a discriminator. Upstream has explicitly deferred the rename to 2.0.

The discriminator is the tool *list*. P1b's error enumerated what the live registry actually offers: `edit, glob, grep, invalid, read, skill, task, todowrite, webfetch, write` (plus `bash` when permitted). **`task` and `invalid` exist only in the V1 registry** — V2's `tool/builtins.ts` has neither, and it also lacks `shell`, `plan` and `lsp`. Their presence proves the V1 registry is what the session prompt path mounted. `stats` independently counted `invalid` usage, so the V1 `InvalidTool` really is in the live path and really fired.

**P7 verdict: the V1 stack fires.** Consistent with the phase-2c source read.

**Correction to that source read:** it listed `ApplyPatchTool` as V2-core-only. It is not — `packages/opencode/src/tool/registry.ts:31` imports it from `./apply_patch` and line 115 instantiates it. The V1 registry is a superset in this respect, and the V1/V2 boundary is about `shell` vs `bash` *implementation*, `permission` vs `permission-v2`, and the presence of `task`/`plan`/`lsp`/`invalid` — not about `apply_patch`.

## 8. The worker environment is not hermetic

Two observations that are about this machine but generalise into a requirement.

**The shell is Git Bash and PATH is inherited wholesale.** P1i's `cmd /c ver` produced:

```
$ cmd /c ver
error: too many arguments. Expected 1 argument but got 2.
$ cmd
Error: Interactive mode requires a TTY terminal.
Please run this command directly in your terminal, not through a pipe or redirect.
$ ver
/usr/bin/bash: line 1: ver: command not found
```

Neither string exists anywhere in the OpenCode source. `which -a cmd` explains it:

```
/c/Users/ponna/AppData/Roaming/npm/cmd      <-- resolves first
/c/WINDOWS/System32/cmd
```

An npm-installed shim named `cmd` shadows the Windows command interpreter. A worker asking for `cmd` got an unrelated tool and reported its error as if it were the command's output. The model then correctly diagnosed the environment as bash, but nothing in OpenCode flagged the substitution.

**Global plugins inject instructions into every worker prompt.** Observed directly in the P4 transcript (§2.1): the model reasoned about "skills" and a "brainstorming skill" that no probe input mentioned, sourced from the globally installed `superpowers` plugin. Vestry composes the task prompt; it does not compose the whole prompt.

Both belong in §15. Vestry owns the worker environment, which means it must **record the policy-relevant subset of it in the audit record** — PATH, shell resolution, and the loaded plugin list — because a worker's behaviour is not reproducible from the prompt and the permission policy alone. It also means binary substitution by PATH collision is a live failure mode: a worker can run something other than what it asked for and report the result as if it had.

## 9. Not performed, and why

**P2a — cooperative abort via `POST /session/:id/abort`.** Not tested. It requires a running `serve` instance plus session creation and prompt submission over HTTP, and the endpoint paths were not re-derived during the probe. Recorded as a gap rather than glossed. Its absence is less damaging than it looks: P2b established the case Vestry must actually handle, since the watchdog's kill is a hard kill and the source read already traced the cooperative path to a real `taskkill /T /F`. What remains unproven is whether that cooperative path *works* on this machine — and the honest position is that Vestry must not depend on the answer either way, because it verifies termination by Job Object enumeration regardless.

**P6 — live server endpoints.** Not tested, for the same reason. Endpoint existence was settled by the source read at this tag; probing them live adds confirmation but no requirement. **No write endpoint was called at any point** — specifically not `PATCH /global/config`, `/global/dispose`, `POST /global/upgrade`, or `PUT`/`DELETE /auth/:providerID`, any of which would have mutated the Owner's real OpenCode installation. `--mdns` was never passed.

**Not covered at all:** concurrency (three workers at once), long-run stability and memory growth, cost accuracy on a paid model, and whether the free router's model rotation affects tool-calling reliability across runs. Free-tier models rotate and rate-limit, so **every pass recorded here is weaker evidence than the same pass on a pinned paid model.** The Owner chose the free router, and that choice is recorded as a limitation on the strength of these results, not hidden.

## 10. Effect on the freeze

D23 freezes the baseline as 1.0 once D20 completes and D21 is settled. D21 is settled and locked. D20's live probe has now run: five of its seven questions answered outright, one answered by a different route than planned (P7), two not performed and recorded above.
