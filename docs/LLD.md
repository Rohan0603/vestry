## 1. Adapter contract — VES-9 / §18 item 1

Traceability: §7–§8, §11–§12, §14–§15; D4–D5, D20, D26; R5/R8. Choice: one capability-driven external adapter, CLI default, owned native execution boundary; no TypeScript SDK or upstream-internal imports. Optional private-server raw HTTP is a separately qualified transport, not an automatic fallback.

### Typed operations

| Operation | Input / output | Invariant |
|---|---|---|
| `discover` | configured executable reference -> installation path, executable digest, version, shell/runtime requirements | Discovery does not invoke a model or silently choose a different installation |
| `qualify` | immutable installation/environment/model/profile fingerprint -> capability manifest + evidence references | Has its own approved qualification scope; no provider or credential probe from ordinary startup, and paid models are excluded by D44 |
| `preflight` | role, profile, policy bytes, model pin, lease/snapshot, current fingerprint -> canary record | Unknown/incomplete final-tool evidence blocks dispatch |
| `start` | committed dispatch intent + fence + role admission -> owned process/session observations | Worker requires current full D27 certificate; other roles require authorized upstream scope, never approval of their future output; all require policy/canary/capability checks |
| `observe` | process handle + ordered input -> normalized events | Every event tied to observed session/attempt; malformed or ambiguous input cannot authorize effects |
| `cancel` | owned attempt and deadline -> acknowledgement + independent termination proof | ACK and proof separate; only supervisor can establish all-owned-process exit |
| `reconcile` | interrupted intent/session/store/OS/Git identities -> known facts or recovery_required | Never silently execute the interrupted tool again |
| `export_evidence` | observed session + authorized store -> sanitized structured evidence in memory | Own redaction precedes any durable/Trello/telemetry sink; no raw export persisted |

`OwnedProcess` is the Rust platform boundary, not a Tokio child reconstructed from a PID: attempt/generation, process identity, owned Job, stdout/stderr readers, root wait, Job enumeration, terminate-owned, proof. Async I/O and state coordination use Tokio; Windows creation uses `windows` bindings. Unix implements group signaling but advertises weaker crash guarantees.

### Manifest and dispatch identity

Manifest fields: schema_version, adapter_id, installation_version, executable_digest, environment_fingerprint, policy_profile_digest, requested_model_pin, qualified_at, platform, evidence_revision, and capability entries `(name, state, conditions, proof_ids, limitations)`.

States are exactly `supported|unsupported|conditional|unverified`. Conditional is usable only when every recorded condition is independently current. Unverified is unavailable. Missing required capability never becomes best-effort. Separate capabilities include final_tool_policy, step_usage, resolved_model_identity, served_model_identity, session_resume, sanitized_export, cooperative_abort, owned_descendant_termination, hard_crash_cleanup, exact_effect_grants, revocation and secret_safe_capture. A manifest cannot turn an inherited global plugin or stored approval into authorization.

`DispatchBinding` is a tagged union. `PreAnchorDiscovery` binds stable goal_id, Owner intake digest/revision, authorized target/snapshot digest, clarification/scratch scope, role, admission, attempt/dispatch ordinal and fence; anchor/criterion/task/Gate-approval fields are structurally absent, never fabricated. Only discovery/charter proposal may use it, with no implementation, plan-node or merge authority. `AnchoredInvocation` requires current anchor/criterion IDs plus role-specific upstream Gate bindings; Worker additionally requires task revision, implementation lease/base and full D27 certificate. Both variants require exact executable digest, canonical argument/config/policy bytes, shell/PATH/plugin snapshot, model pin and credential **references**. Missing required fields in either variant deny; environment fingerprints exclude secret values and use references/version identifiers for secret-backed configuration.

Pre-anchor admission revalidates the unchanged Owner intake, target allowlist, scratch-only effect profile, clarification budget and process ownership instead of running predicates over an invented anchor. At Gate 1 the writer atomically freezes the approved anchor and changes the goal to anchored state; outstanding discovery admissions are invalidated, never retroactively relabelled as anchored. Every later admission runs D33 drift predicates and cites criteria, including Architect/Planner/Reviewer. The baseline's pre-anchor wording tension is resolved by D37 (revision 1.3, Owner-decided 7 November 2026): discovery-only dispatches bind the Owner's durable intake/target/scratch scope, and every dispatch from the frozen anchor onward carries full D33 traceability without exception. This design implements that scope boundary; it introduces no post-Gate-1 exemption. If an operation cannot be classified into the discovery-only boundary, it waits for the approved anchor. [D33, D37]

### Per-dispatch environment

Construct from an explicit allowlist, not wholesale inherited environment. Resolve Windows executable/shell paths without ambiguous PATH lookup; record the safe effective PATH and resolutions. Secret values are obtained only for an explicitly approved operation and injected into that owned child; never interpolate into prompts/argv/logs/evidence.

- Set validated `OPENCODE_PERMISSION`; preserve object order with wildcard first, specific matches after. Reject malformed JSON locally before OpenCode starts.
- Set `OPENCODE_DISABLE_PROJECT_CONFIG` and `OPENCODE_DISABLE_AUTOUPDATE`; isolate `OPENCODE_DB` with a Windows-absolute per-attempt path and verify actual store identity, not merely environment spelling.
- Supply explicit config content and approved agent/model profile. Reset additive config-directory and experimental overrides rather than inherit them.
- Clear auto-approval aliases, automatic sharing, unapproved MCP/custom-tool/plugin configuration, provider env credentials and OTLP endpoints/headers from inherited input. Never send `always`; persisted permission stores remain isolated.
- Pin `OPENCODE_GIT_BASH_PATH`/shell resolution where used; reject unexplained executable mismatch.
- `OPENCODE_PURE`, default-plugin suppression, XDG config/data/cache/state relocation, valid `OPENCODE_AUTH_CONTENT` and home discovery controls are **qualification candidates**, not proven hermetic switches. A fresh XDG data root also changes the auth-file location; do not copy the Owner's auth store. Additional managed/home/custom-tool sources must be enumerated or the profile remains unverified.
- For any server-bearing path, including an embedded server if exposed by `run`, independently establish loopback binding/auth behavior. Private `serve` requires ephemeral discovered port, explicit 127.0.0.1 and distinct memory-only password injected into the child. No mDNS, CORS expansion, auth mutation, global config mutation, dispose-all or upgrade routes.

Plugin-source contradiction: O5 directly shows a headless pure guard, unlike the historical narrative. Record configured origins and, separately, machine-observed loaded origins; absence of a configured entry is not proof nothing loaded. Existing evidence is unchanged; re-probe before promoting suppression.

### D26 canary protocol

1. Check current version/binary/config/role/model/fence; parse and order-preserving serialize the actual policy. A malformed-policy negative test must fail before a real child/model call.
2. Run inspection in an owned qualification context: `debug config` and `debug agent <name>` without `--tool`. Parse resolved ordered rules and enabled tool map. Inspect the dispatch model, not an unrelated default model. These commands can perform dependency/auth-related initialization and are not intrinsically side-effect-free.
3. Run a **deny-all canary dispatch** before real work on this dispatch path. Hard-deny tool exposure under the canary policy; use the pinned authorized provider and model and a disposable scope. No grants are inferred from its prompt.
4. PASS only if machine evidence explicitly identifies the relevant final tool inventory or an unavailable-tool error with a complete list proving the target effect tool absent. Correlate session/role/model/version with the canary, and bind the observed final inventory to the executable/version/config/plugin/policy/route fingerprint. Mere lack of `tool_use`, model prose, no created file, or debug inventory alone is insufficient.
5. Require positive-control/negative-control qualification: expected available tool in a safe authorized profile; absent tool under deny; reversed-order policies; malformed payload; role/model/plugin/MCP differences; stale fingerprint; wrong store. Positive controls must not authorize privileged effects casually.
6. One bounded canary retry is permitted within the attempt budget when observable evidence was not produced; otherwise NOT RUN/unverified and no real dispatch. Never continue just to avoid a stalled queue.
7. Bind proof to the actual work profile and verify its ordered rules/config before launch. Deny-all canary does not prove every rule in a different real policy. Any change to policy, model, installation, plugins, store or source revision invalidates qualification/certificate.

**Unresolved proof boundary:** no supported final-session attestation is established for every custom/MCP/provider tool path at this tag. Restrict the admitted profile to demonstrated paths; if no such profile passes D26, the milestone blocks. This is an honest design answer, not a synthetic canary PASS. O1–O3.

**Bounded feasibility experiment (target, NOT RUN):** a disposable-scratch experiment, pinned to the exact executable digest, exercises deny-all and actual-policy ordering cases, custom/MCP/config variation, and machine-correlated final-tool evidence; it writes an immutable safe result that expires/invalidates on every fingerprint change. Malformed policy is rejected locally before any child/model call. Negative tests must distinguish an **ask rejection** (the tool is present but its permission request was denied) from an **absent denied tool** (the tool is not in the final inventory); only the latter substantiates the deny-all inventory claim, and the two are recorded as distinct outcomes. No authorized real work is used as the experiment, and no second server adapter or hidden instrumentation is assumed. Until a supported observation/parser is demonstrated, canary capability is unavailable and dispatch fails closed. [disposition #18; O2, O7]

### NDJSON ingestion

Incremental UTF-8 framing; proposed maximum line 1 MiB, bounded queues, separate stderr drain. Preserve outer `step_finish` versus inner `step-finish`. Require observed session, part/message identifiers and nonnegative finite counters/cost; reject invalid values rather than coerce to zero. Deduplicate usage by attempt/session/part identity; token totals are not recomputed by blindly adding `total` to components. Cache/input accounting retains upstream definitions. Record snapshots as upstream provenance, not necessarily the current Git worktree SHA.

Permission-rejection text is a separate bounded/redacted diagnostic channel, not valid NDJSON and not a canonical action grant. ANSI/multiline/unknown lines are classified explicitly. A secret-shaped payload is redacted before persistence. Output overflow must produce an integrity finding; it cannot silently discard mandatory usage/evidence. Backpressure protects memory, but never excuses starving stdout/stderr or inventing progress.

Fresh CLI runs omit `--session`. Resume uses only observed session IDs after reconciliation. Exit 0 requires a complete valid stream and independent verification before any success claim. No `done` event is invented. CLI cancellation initially uses owned Job termination; cooperative `serve` abort remains unavailable until VES-24/VES-25 proof.

## 2. Chief LLM invocation and effect gateway — VES-10 / §18 item 2

Traceability: §5–§7, §15–§16; D7, D21, D30. Choice: the same adapter for Architect/Planner/Worker/Reviewer and optional verifier judgement, with a typed role and capability profile; no second LLM client.

Architect/Planner receive explicitly selected redacted snapshots and a scratch output area, not a writable implementation worktree or privileged shell. Typed proposal output contains criteria, contracts, dependencies and provenance. The Chief validates it and alone commits authoritative decisions/plan records or project-record writes. A read-only prompt is not enforcement: target mutation, direct egress and nested task tools must be denied/qualified independently; unavailable enforcement keeps the role profile unavailable.

Workers receive exactly one D27-certified task and a fenced lease. Reviewer is a new attempt/process/session, distinct from all producing attempts, with an immutable candidate SHA and no fix permissions. A failed/ambiguous review is input to the Chief, never self-approval. Both use measured per-step usage. All roles use current role admission, policy/canary/ownership checks and the three process slots, but full D27 Worker certification does not bootstrap its own pre-Gate-3 outputs.

| Role admission | Already-authorized inputs | Output boundary |
|---|---|---|
| Discovery/charter proposal | Owner intake, target binding, explicit current policy and bounded clarification scope | Produces Gate 1 proposal; cannot require an already-approved charter |
| Architect | Gate 1 anchor + authorized architecture scope and allowed read/scratch profile | Produces HLD/LLD for Gate 2; cannot require its own future design approval |
| Planner | Approved Gate 1 and Gate 2 digests + planning scope/profile | Produces plan for Gate 3; cannot require its own future plan approval |
| Worker | Gate 1–3 bindings + full current D27 certificate + lease/fence | Implements one task, never modifies acceptance/policy |
| Reviewer/judgement invocation | Chief-owned review/check intent + exact candidate/evidence + read-only role profile | Advisory independent verdict; no implementation or self-approval |
| Chief/Doctor/Messenger/deterministic Verifier | Native typed state/effect operations, not an LLM admission | Optional verifier judgement uses the same adapter; deterministic roles never acquire a second LLM client |

`invocation_admissions` records role, upstream artefact digests, policy/capability/canary refs, snapshot/fence, budget reservation and generation. Missing upstream approval blocks the appropriate phase; missing future artefact never becomes a fabricated certificate. Test discovery -> Gate 1 -> Architect -> Gate 2 -> Planner -> Gate 3 -> Worker with no synthetic approvals, including unavailable capabilities before every phase.

### Exact-action grant contract

`ActionRequest` contains schema_version, action_id, actor_attempt, role, the §1 tagged scope binding (goal/intake/scratch only for PreAnchorDiscovery; required goal/anchor/criteria for AnchoredInvocation), lease/fence, operation enum, target repository/path/branch/destination, base/candidate SHA, typed args using secret references, expected_state_digest and current policy_revision. Proposed boundary: JSON ≤64 KiB; reject unknown operation/field, unsafe target, nonfinite number and inconsistent scope before evaluation. Read/write/execute/send are distinct permissions.

`Approval` binds canonical request digest, target digest, reviewed SHA where applicable, policy revision, grantor identity, issued_at_ms, finite expires_at_ms and single-use state. Canonicalization hashes **references**, never secret values. Missing/non-numeric/expired expiry denies. Expiry is assessed conservatively after clock discontinuity/restart; unsure grants are denied rather than extended. Approval is not inferred from issue text, a marker, a model response or another command's grant.

Chief-owned effect flow:

1. Validate request and obtain actual diff/target snapshot; classify against current policy, including upward risk changes. Hard denials remain denied in every mode.
2. Tier A uses its explicit allowed scope; Tier B requires recorded matching Owner clause or approval; Tier C always requires the Owner. No YOLO alias is passed by convenience.
3. Fence conflicting worker mutation and independently bind current target/SHA. In one writer transaction compare request, policy, fence, expiry and unconsumed grant; consume grant, append audit and commit effect intent.
4. Immediately invoke the fixed typed executor without returning a privileged reusable allowance to the worker. `expires_at` bounds admission at the last gateway evaluation; the irreversible effect itself cannot be transactionally atomic with SQLite. Delayed/unstarted intents are not dispatched after expiry or restart.
5. Record observed result/read-back in a transaction; uncertain outcome parks and never reconsumes/replays the grant. Lost approval after consumption is acceptable fail-closed, duplicate effect is not.

Revocation changes the policy revision. No queued unstarted request from the withdrawn class may pass evaluation. Already-admitted in-flight effects are not retroactively re-judged, matching §15. Reconcile them, and park dependent workers with BLOCKED and exact unblock condition. Tests must distinguish queued, admitted, running and uncertain effects.

**Capability exclusion:** stock CLI patterns cannot implement this for arbitrary worker shell operations; private-server `once` is approval-request-level and lacks expiry/digest attestation. The typed executor is a draft target. Unresolved filesystem/effect/egress enforcement is a **hard profile-availability gate**: until worker effect restriction, target isolation and allowed egress are qualified, privileged execution is unavailable. A permitted arbitrary shell/build can spawn descendants that bypass a nominal typed gateway, so command-name allowlists and `once` are not exact-action/expiry authorization. The daemon owns typed effect intents — scoped action digest, policy revision, revocation check and observed result — with external confinement qualified separately; native process/lease control is not an OS sandbox, and arbitrary build scripts cannot be assumed safe because their command prefix is allowlisted. **This integration does not exist and is not claimed to exist.** Read-only roles receive no target-mutation authority merely because a prompt or scratch directory says read-only. [disposition #31; O3, O7]

## 3. State schema and transactions — VES-11 / §18 item 3

Traceability: §10–§12; D3, D27–D33, D42. Choice: bundled SQLite WAL, one dedicated writer thread owning its connection; bounded command queue; short read snapshots only after migrations. Read connections enable foreign_keys and do not mutate. Set/check WAL, synchronous FULL and busy timeout; no SQLite blocking call on a Tokio executor thread.

IDs are opaque stable identifiers — for the project record, the Trello board/list/card/comment ids, never display names, short links, list positions or card order; SHA/digests use explicit algorithm/version. Timestamp fields are UTC integer milliseconds except exact Win32 creation FILETIME (stored losslessly). State enums are constrained; no null-as-success. Foreign keys and scoped unique keys enforce relationships; writes use expected-revision compare-and-set.

### Loss impact / survivability supplement

No table loss is silently repaired from GitHub/Trello narrative. Affected writes/dispatch stop; read-only Doctor and intact independent goals may survive only after integrity/ownership checks. Recovery restores a validated coherent backup plus referenced safe evidence; it never fabricates approvals, zero budgets or remote effects. Per-table loss effect:

- `schema_migrations`, `daemon_generations`: schema/ownership unknown; all write startup unavailable.
- `projects`: repository/tracker scope unknown; project writes unavailable.
- `goals`, `clarification_requests`, `issue_budgets`, `repair_cycles`, `watchdog_episodes`: intake/counters/reservations unknown; affected dispatch/retry/clarification unavailable, no reset.
- `anchors`, `criterion_defs`, `anchor_criteria`, `charter_amendments`, `gate_artefacts`, `gate_decisions`: intent/approval/constraint history unverifiable; affected admission and acceptance unavailable.
- `tasks`, `task_edges`, `task_criteria`, `runs`, `attempts`, `leases`, `invocation_admissions`, `dispatches`, `owned_processes`: work/traceability/ownership unknown; `recovery_required`, no replacement launch or process kill from a guessed PID.
- `policies`, `action_requests`, `approvals`, `effect_intents`: authority/effect outcome unknown; no mutation/replay/refund.
- `readiness_certificates`, `check_manifests`, `check_results`, `reviews`, `evidence`, `object_criteria`: proof chain incomplete; no Ready/acceptance. Fresh independent checks may produce NEW evidence after authoritative state is restored, never reconstruct lost approval.
- `capability_manifests`, `canary_results`: qualification evidence unknown; affected admissions/dispatches invalidated, re-qualification required.
- `usage_steps`: spend/usage unknown, not zero; affected capability qualification unavailable.
- `trello_mappings`, `outbox`, `inbox`: remote outcome/order/idempotency unknown; no blind resend; bounded read-back reconciliation.
- `audit_events`: chain integrity unavailable; affected writes stop.
- `attention`: unexamined findings cannot silently disappear; restore/rederive from complete authoritative finding events, otherwise blocked.
- `memory_facts`: optional recall unavailable; cannot recreate an authoritative decision from remembered prose.
- `adapter_stores`: session identity/recovery evidence unavailable; preserve on-disk candidates, no blind deletion or resume.

SQLite backup and atomic-commit semantics support coherent **local** recovery, not remote atomicity (L7). Backup/restore/migration/crash tests are NOT RUN. [disposition #22]

Migration order respects foreign-key dependencies: referenced tables are created before referencing tables. ### Lifecycle transitions and integration handoff

Goal phases are `discovery|architecture|planning|executing|integrating|awaiting_acceptance|blocked|accepted`; gate decisions bind artefact digests. Task states are `planned|ready|running|verifying|reviewing|repair_pending|verified_handoff|integrating|blocked|recovery_required|integrated_closed|withdrawn|cancelled`. Only `integrated_closed|withdrawn|cancelled` are terminal. `verified_handoff` remains open for integration and is never projected as a Done-list card. Attempt states separately record `reserved|launch_intent|running|verifying|reviewing|succeeded|failed|cancel_pending|cancelled|recovery_required`; attempt success does not close its task. Task cancellation is terminal only after independent owned-process termination and preservation of pending changes/effects; otherwise it is `recovery_required`.

| Transition | Required observation and atomic record | Disallowed shortcut |
|---|---|---|
| Gate-approved plan -> `ready` -> `running` | Current Worker D27 certificate, admission and fenced launch; observe owned root | A Backlog/Ready list position or a remote Done card is not dispatch authority |
| `running` -> `verifying` -> `reviewing` | Immutable candidate SHA, independent checks and fresh reviewer bound to that SHA | Worker success is not verification; a new commit invalidates both |
| Failed check/review -> `repair_pending` | Stable issue repair reservation plus failed-candidate evidence; replacement needs fresh admission | New task revision/run/attempt cannot reset repair count |
| Successful checks/review -> `verified_handoff` | Current exact-SHA proofs, source/evidence bindings, HANDOFF/REVIEW HANDOFF outbox | No merged-SHA claim or CLOSEOUT |
| Retire execution lease | All owned processes independently gone, every change recorded with candidate/base bindings; preserve user dirty state and retained worktree/artifacts | Lease retirement neither deletes the retained source nor closes the task |
| Successor admission from handoff | Mandatory dependency has current independently verified/reviewed candidate; compose and bind successor base explicitly, recheck D27 | Mutable branch head, remote Done or conflicting candidates are insufficient |
| Handoffs -> `integrating` | Integration snapshot composes the candidates; independent combined checks/review; invalidate changed-SHA proofs | Children passing cannot prove combined integration |
| `integrating` -> `integrated_closed` | Owner-authorized reviewed merge independently read back, exact merged SHA, valid applicable proofs and atomic CLOSEOUT/status outbox | Pending PR/approval is not a merge; no automatic merge |
| Integrated goal -> `awaiting_acceptance` -> `accepted` | Every issue in the approved plan is `integrated_closed` with complete independently valid attached proofs and confirmed remote closure; all root criteria PASS, current integrated review/evidence, no orphan work/unresolved blind spots; Owner acceptance bound to that exact bundle | Traced blocked/cancelled/withdrawn work, pending closure, child completion or a revised easier anchor cannot satisfy planned-issue closure |
| Any uncertain effect/ownership -> `recovery_required` | Doctor finding, retained bindings/changes, precise BLOCKED condition | No replay, grant refund or clean cancellation by inference |

The sequencing discrepancy is resolved by D36 (revision 1.3, Owner-decided 7 November 2026): the former §6 Phase 4 close-before-integration wording is superseded. Execution ends in `verified_handoff`; closure and merged-SHA CLOSEOUT occur only after the Owner-authorized, independently reviewed Phase 5 merge is observed. The remote workflow mapping must conform to that order; pending merge remains visible and retained, and no closure capability may fabricate Done/CLOSEOUT before the observed merge. Multi-issue integration tests must cover a successor from retained handoff, conflicting bases, pending merge, changed integration SHA, revoked merge approval, crash around merge/read-back/CLOSEOUT, and premature lease/source deletion. [D36]

### Durable repair and diagnosis reservations

Before starting a repair, the writer compares `issue_budgets.repair_count < 2` for the stable `(project_id,issue_id)`, reserves the next ordinal in `repair_cycles`, increments the count, creates the linked repair attempt/intent and commits audit/outbox together. A unique scoped trigger_key with identical failed-candidate digest returns the existing reservation; differing content conflicts. Rejection after two repairs parks that issue. Replacement attempts, task revisions, daemon restarts and new runs retain the same issue budget. Crash before commit consumes nothing; after commit the reservation stays consumed even if dispatch is uncertain. Reconciliation observes the existing intent rather than refunding or dispatching another repair.

A watchdog episode binds attempt_id and the stalled durable-progress sequence. Its one diagnosis retry is atomically reserved in `watchdog_episodes` with the attempt retry-count increment, retry intent and audit/outbox, only when retry_count < 2. An existing episode cannot reserve again; a later episode cannot exceed the same attempt cap. Repair count and attempt retry count are separate limits; an ordinary retry cannot be relabelled to evade a failed-candidate repair reservation. Fault cases include concurrent duplicate triggers, mismatched same keys, crash at reservation/spawn/read-back, cap boundaries, renewed progress followed by another stall, and restart/replacement with exhausted budgets. Clarification uses the corresponding stable-goal reservation in §6.

Ordinary retries and the watchdog's one retry retain the **same attempt_id and retry_count**, allocating a new dispatch ordinal; only an independently failed-candidate repair reservation creates a new repair attempt. Operator restart, transport failure, lost stream or missing canary output cannot create a fresh attempt to reset the cap. Two retries exhausted makes that attempt `recovery_required`; an unresolved transport/ownership/effect outcome cannot be converted into a repair to bypass reconciliation.

Before any retry dispatch, independently establish that the preceding owned root and descendants are gone, reconcile its session/effects/source and preserve all changes. ACK, EOF or root exit alone is insufficient. Uncertain termination/effect outcome parks with no replacement launch. Retire the preceding dispatch's active ownership, increment retry_count, allocate ordinal, advance lease fence, invalidate old admission and commit retry intent/audit together with revision compare-and-set; a unique active-dispatch constraint prevents concurrent reservations. The new dispatch needs fresh role admission/canary and, for Worker, current D27. It gets a fresh owned Job with no overlap with the previous Job; late events carry the old fence and are rejected. Known session resume can recover context but never silently replay an interrupted tool. Tests: two schedulers race a retry, still-live grandchild blocks replacement, stale event after fencing, unknown effect cannot relaunch, and repeated restarts retain the exhausted count.

### 8.1 Pin tuple, storage and audit

The pin is the manifest field `requested_model_pin` (§1/§3), not prose. Revision 7 fixes the tuple as `(pin_revision, target_kind, provider, logical_model, api_alias_or_tag, weight_digest, runtime_version, model_details, endpoint, route_policy, identity_channel, adapter_executable_digest, adapter_version, config_digest, credential_ref, allowed_variants)`. `target_kind` is `local-open-weight` or `free-tier`; nothing else is admissible under D44. `route_policy` records `allow_fallbacks: false`, the explicit `order`/`only` provider slug, `require_parameters: true`, `data_collection: deny` where the provider supports it, and the disabled model/provider fallback flags. `identity_channel` names the §8.2 row used to obtain served identity. `allowed_variants` records the permitted provider slugs rather than assuming a base tag pins one service variant. `model_details` carries the local runtime's `format`, `family`, `parameter_size`, `quantization_level` and `size` where reported.

The tuple is stored in the dispatch intent and the capability manifest, audited as a canonical safe digest in the hash-chained audit event with the credential **reference** only (§9), and displayed with its D32 status (§8.6). A pin revision is immutable: changing any field creates a new `pin_revision` and requires the fresh canary, manifest and approval path (§8.5); there is no in-place edit. Evidence records never contain credential values, provider headers or raw payloads (§15).

*Authenticated* means only this: the field is obtained from the pinned, allowlisted endpoint using the pinned credential reference, correlated with a provider-issued response/generation identifier, and recorded before acceptance. It does not attest weights, hardware or the absence of substitution. The local digest is the stronger claim because it is a content digest of the served blob, but it still depends on the pinned runtime reporting it honestly. If a channel is absent or unparsable for a run, that run is `NOT RUN` for the pin and the channel's §8.6 row returns to `target`. If the channel has never been verified for the provider, the profile is `unverified` and dispatch is blocked; no design text promotes it.

### 8.3 Detection cadence and mid-session transition (G2)

The pin is checked at six points: (1) admission — a current pin revision exists, is inside the D44 population, and adapter/config/policy fingerprints are current; (2) pre-dispatch — local digest query, provider eligibility (`modelStage`, `retirementTime`), and verification that the applied route policy matches the pin; (3) per response — Gemini `modelVersion`/`responseId`, OpenRouter generation id, local digest fixed for the loaded model; (4) post-hoc read-back — OpenRouter before attempt acceptance, Gemini at attempt close; (5) resume — pin, digest and recorded identity revalidated before the session continues; (6) closeout — the evidence record is classified (PASS only on a matching identity and all other criteria).

If identity diverges after step *n* — a different served model, a fallback attempt, a missing identity, or a local digest change — the adapter sets a fence that refuses new step dispatch, governed effects and tool execution; halts the worker through the owned-process boundary with independent termination proof (§1); records the discrepant fields safely; and raises attention. The attempt is `NOT RUN` for the pinned model from the divergence step with its reason; earlier observed steps are not promoted to a pass and the attempt never becomes `PASS` by substitution. The mismatched session is never resumed under the pin. A new attempt is a new dispatch under the same pin with a fresh preflight and canary; re-pinning to the newly served identity is a §8.1 new pin revision and, for the product, an Owner decision — never an agent choice. Continuing silently, re-routing, resuming the mismatched session or relabelling the run are forbidden.

### 8.4 Local weight-digest verification at dispatch (G3)

The local pin is `(runtime, api_alias_or_tag, weight_digest, size, model_details, runtime_version)`, where `weight_digest` is the runtime's `digest`, defined as the SHA-256 digest identifier of the model contents. At every dispatch and resume Vestry queries the pinned runtime's `/api/tags` directly over the pinned loopback endpoint and compares `digest` and `size` (and `details.quantization_level`/`family` where reported) with the pin. It does not use OpenCode's discovered inventory or a cached list as proof: discovery caches a last successful inventory and can be stale during a runtime outage.

The tag is not identity. A re-pull can move `qwen3:8b`-style tags to a new build; the digest comparison turns that into `BLOCKED`, never a silent pass. Mismatch, a missing model, an unreadable response or an unexpected endpoint → the attempt does not run and the item is `BLOCKED`; the observed digest is recorded as safe evidence. A new digest is a new pin revision: it requires fresh qualification of the adapter behaviours, a fresh canary and the Owner's pin selection; Vestry never auto-adopts the newly pulled build. The runtime version and model-store path (`%HOMEPATH%\.ollama` or `OLLAMA_MODELS`) are part of the fingerprint, and a runtime update invalidates the manifest. Whether Vestry supervises `ollama serve` as an owned child or requires an Owner-managed service is recorded with the pin; either way the exact endpoint is verified before dispatch, and the tray app is not assumed to be the pinned version. The digest identifies content, not quality (D44).

### 8.5 Pin ↔ canary ↔ policy envelope (G4)

- **Canary.** D26 preflight runs on the pinned target through the same route policy. A canary that would need a different model or provider is `NOT RUN` and blocks dispatch. Its record binds the pin revision, digest/identifier and provider variant; the adapter executable digest and version; the config/plugin/policy digest; the final-tool inventory evidence; and the observation time.
- **Invalidation.** Any §8.1 field change invalidates the canary record, the capability manifest and any D27 readiness certificate. A new model does not inherit an old envelope: the pinned model's tool-calling behaviour is re-observed, because changing the model can change what a policy means in practice.
- **Admissible pins.** D44 is the admission constraint: exactly a pinned local open-weight model identified by weight digest, or one pinned free-tier model identified by provider and exact identifier. No paid route, price tier or charge authorization is admissible, including through a provider default, an error path or an `:free` variant that silently upgrades. A secondary provider is not an automatic fallback; it can only exist as a separately pinned and approved target for availability, never as a silent substitution.
- **Capability transitions.** `unverified → supported` requires a recorded live `PASS` at the exact fingerprint, reviewed independently, not a design statement. `supported → unverified` is automatic on any fingerprint change or invalidated evidence.
- **Requalification triggers as data.** The following rows are evaluated before every dispatch; a change invalidates the named artefacts and forces the named re-run.

| Trigger | Invalidates | Re-run before dispatch |
|---|---|---|
| Adapter executable digest/version | manifest, canary, certificate | discover, qualify, canary |
| Local model digest/size/details | pin, canary, certificate | stop; new pin revision, qualify, canary |
| Provider model version/stage/retirement | served capability, canary | re-verify identity; re-pin if changed |
| Endpoint, route policy, fallback flags, allowed variants | pin, canary | new pin revision, canary |
| Credential reference version | capability, certificate | re-verify credential reference path |
| Policy/config/plugin/tool registry | canary, manifest | canary with final-tool evidence |

### 8.7 Failure taxonomy (G6)

`BLOCKED` below is the item/work state under D44; D29's evidence states remain exactly `PASS`, `FAIL` and `NOT RUN`, so every row records the attempt as `NOT RUN` with its reason, never as a fourth state and never as a failure of model quality.

| Condition | Evidence state | Item/work state | Permitted action | Never-paid invariant |
|---|---|---|---|---|
| 429/quota exhausted before inference or identity evidence | `NOT RUN` (availability) | `BLOCKED` | Bounded retry with backoff on the identical pin and route; record the bound; no model or provider switch | No paid route or credit purchase is a fallback |
| 429/timeout/connection loss after inference began or with a lost response | `NOT RUN` (unknown outcome) | `BLOCKED` | Reconcile the unknown outcome; no blind replay of the attempt | No substitute model is used to "recover" |
| Model retired (`RETIRED`, passed `retirementTime`, provider "unknown model") | `NOT RUN` | `BLOCKED` | Requalification and a new pin decision; no auto-upgrade | A successor model cannot inherit the pin's pass |
| Provider fallback used (`provider_responses[]` > 1, differing `provider_name`, differing `model_permaslug`) | `NOT RUN` (substitution) | `BLOCKED` | Record every attempt; re-pin only by the §8.1 path | Any fallback is a substitution event even if the final model matches |
| Served identity missing or unparsable | `NOT RUN` | `BLOCKED`; channel row returns to `target` | Diagnose; treat the profile as `unverified` until demonstrated | Identity opacity is never resolved by trying a different model |
| Served identity differs from the pin | `NOT RUN` | `BLOCKED` | Fence, halt, record, requalify; no session resume | The substitute's result is never the pin's pass |
| Identity or digest changes mid-session | `NOT RUN` from the divergence step | `BLOCKED` | Halt and fence (§8.3); fresh attempt only | No mid-session re-route |
| Local digest mismatch or missing | `NOT RUN` | `BLOCKED` | Do not run; new digest needs a new pin revision and approval | An unverified build is never run |
| Transport/auth error before model contact (401/403, transient 5xx) | `NOT RUN` | `BLOCKED` | Fix the credential reference or config; bounded retry only for transient 5xx on the same pin | No credential or model escalation |
| Auto/opaque route or alias that may rotate | `NOT RUN` | `BLOCKED` | Remove the auto route; re-pin explicitly | A rotating router is not a pin |

No row is a `PASS`. No row permits a paid route, a paid price tier, a charge authorization, a second provider as a silent fallback, accepting a substitute as the pinned model, or marking an attempt `PASS` on absent evidence. A bounded retry never changes the pin and never re-runs an ambiguous governed effect (§12).

Qualification and re-proof content is **synthetic only**: fixed harmless prompts and tool-call fixtures. No repository content, prompt, credential or Owner data is sent to a free tier, and the Gemini free tier's product-improvement use of inputs is avoided by construction rather than by policy hope. Probes are not part of this design pass and remain NOT RUN.

## 12. Trello wire protocol — VES-20 / §18 item 12

Traceability: §10–§12, §19 item 11; D21, D28–D29, D42. Carrier: the bound Trello board (D42) — markers are card comments, never card descriptions, checklist items or list positions. Board/list structure and card content are the schema below. Choice: exact heading plus a fenced JSON block; semantic canonical read-back, append-only history, sequence/key dedupe. Marker names remain `START`, `PROGRESS`, `BLOCKED`, `HANDOFF`, `REVIEW HANDOFF`, `CLOSEOUT`.

### Board, list and card schema

Board/list structure and card content are the part of the project record that baseline §10 assigns to this design. They are card content, not markers; markers stay card comments.

- **Lists are the status.** One bound board per project, exactly one list per card, and identity by board/list/card id — never display name, short link, list position or card order. The eight workflow lists are `Backlog`, `Ready`, `In Progress`, `Blocked`, `In Review`, `Done`, `Canceled` and `Needs Project Verification` (migration quarantine only: never a runtime queue, never written by the runtime). The §3 task states project as `planned`→Backlog, `ready`→Ready, `running`/`verifying`/`repair_pending`→In Progress, `blocked`/`recovery_required`→Blocked, `reviewing`/`verified_handoff`/`integrating`→In Review, `integrated_closed`→Done, `withdrawn`/`cancelled`→Canceled. `repair_pending` projects to `In Progress` because the card has been returned to its worker with an open repair reservation and its review is over; that is the `In Progress` option of the merged governance transition "`In Review` → `Ready` or `In Progress` … review requests changes", chosen so a repair never masquerades as a fresh `Ready` card or a still-open review. The In Review move follows the published review handoff, never branch creation alone. A move is written only after the local transition commits (the transaction/effect pair in §3) and is never authority: dispatch, certification and acceptance never read list membership as proof, and work in `verified_handoff` or `integrating` is not projected as Done before the observed merge.
- **Classification is description text.** Native labels cannot be created or named through the connector (six unnamed defaults, zero uses — L1), so the description carries the adopted taxonomy: exactly one primary role token (`chief`, `worker` or `human`; `metadata-bootstrap` only as the `worker` adjunct), exactly one Type (`Research`, `Architecture`, `Implementation`, `Bug`, `Verification`, `Governance`, `Release`), component identifiers naming the affected subsystems (one or more stable tokens, recorded as `none` only where the approved plan classifies the record as cross-cutting, so the field is never silently absent), Priority `P0 Critical`–`P3 Low`, Risk `Normal`/`Elevated`/`Critical`, dependency references as `blocked by <card id or url>`, and a source backlink to the originating issue or pull request. It is written as one whole-document update compared against the read-back text, and a role change is proven by that text plus the handoff comment, never by a list move. No secret, credential or hidden state enters the description.
- **Acceptance items are a native checklist.** Each card has exactly one **acceptance checklist** — runtime-created cards and every card without a legacy task list use `Acceptance items`; a migrated card that carries the historical `GitHub task list (migrated)` keeps it and gains `Acceptance items` as a **separate** checklist when its acceptance items are first written. Acceptance items are never appended to the migrated list: that would mix migrated legacy items with acceptance items and break the stable-id identity and the read-back below. The migrated `GitHub task list (migrated)` checklist is a **historical record**: its presence and item text are retained, the runtime never edits it, its checked states are migrated legacy state exempt from the projection invariant, and a card migrated without one is not an unknown outcome — it simply has no legacy task list and therefore no migrated legacy state. Any other checklist is foreign content: never treated as acceptance items and never edited by the runtime. The acceptance checklist holds one item per approved criterion or task acceptance item with the stable criterion/item id in the item text; items are written when the specification is approved and are current only while their text matches that revision. Its checked state is a projection: an item is checked only after the corresponding `check_results` row is a valid PASS on the current candidate and is unchecked again when that result is invalidated. Only the Chief writes checklist state; a Worker cannot check items to claim success, and neither an acceptance item nor a migrated legacy checked item is ever acceptance proof on its own.
- **Read-back** covers these values — the card's actual list, the description taxonomy text including its component identifiers, the acceptance checklist's item text and checked state, and the retained presence of the `GitHub task list (migrated)` checklist on cards that were migrated with one (its legacy item states are recorded as historical and not re-projected) — together with the marker and evidence values required below, comparing semantic values rather than Markdown whitespace. A missing acceptance checklist where acceptance items were written, a migrated checklist that disappeared or was altered, or differing or unreadable values are an unknown outcome that parks, never a blind retry.

Envelope fields: protocol=`vestry-marker-v1`, marker, key, board_id, card_id, aggregate_seq, binding_kind with goal/anchor/criteria or discovery intake reference, applicable task/run/attempt refs, actor_generation, source_revision, timestamp_ms, safe typed payload. The canonical payload is versioned typed JSON with a stable operation key, aggregate sequence and source/actor/object bindings; its digest is computed excluding the digest field itself. The same §1 tagged-union rules apply; discovery cannot fabricate anchor/task refs or use CLOSEOUT to claim planned work completed. Heading must match marker. Unknown version/type, wrong board, missing/oversized fields or same key/different digest is rejected and audited. Marker parsing extracts one well-formed designated block, not text guesses or arbitrary code fences; presentation/Markdown whitespace is not authority.

Payloads preserve baseline fields: START approach/source/dependencies/branch/base/expected diff/tests/risks; BLOCKED precise blocker/owner/unblock condition; REVIEW HANDOFF checklist/tri-state results/PR reference or explicit NOT RUN/exact SHA/limitations/security/rollback/reviewer action; CLOSEOUT merged SHA/criteria/remaining linked follow-ups. If merge has not happened, do not manufacture CLOSEOUT. Warnings use PROGRESS and remain nonblocking.

Outbox orders all marker/status operations for a card under one aggregate sequence; at most one inflight. Before a retry, page the card's comments and reconcile key+canonical JSON digest+mapped comment identity; compare semantic JSON, not Markdown whitespace/strikethrough. Read-back verifies the board/list/card identity, the card's actual list, its description taxonomy text including component identifiers, its acceptance-checklist item text and state, the retained presence of the migrated checklist where the card was migrated with one (legacy checked state recorded as historical, never re-projected), comment text, attachments/evidence identity and payload. Connector capability/pagination gaps mean unknown outcome and BLOCKED, not safe duplicate retry. A list move is a status projection, never proof that a marker was written or a CLOSEOUT observed. The Trello representation of a task's remote closure is therefore the card in the `Done` list together with a read-back of card identity and the `CLOSEOUT` comment; Trello's `closed`/archive flag is a separate visibility state and is neither closure evidence nor a deletion.

Remote APIs without atomic idempotency/create keys cannot promise physical exactly-once. A write intent with possible transmission becomes uncertain before sending; after crash query it, do not simply resend. Serialize writers, deduplicate known records, and park if no definitive observation is possible. Preserving a possibly unsent intent is safer than committing a duplicate effect. START/CLOSEOUT keys are stable across daemon restarts. Unique local keys do not confer server-side exactly-once creation.

On a lost create response: preserve the uncertain effect intent and exhaust bounded paginated read-back for the exact destination/key/digest and actor. One matching record may confirm the write; zero matches in an eventually consistent read does **not** prove no write occurred; multiple or different matches park. Never blindly repeat an uncertain creation. A GitHub webhook path, if one is later added for repository events, retains `X-GitHub-Delivery` for transport deduplication, but that header is not a universal content-write transaction and is outside the D42 project-record write path. Under D42 the **product** project record is the bound Trello board; that Owner decision changes the carrier, not SQLite runtime authority, and no product acceptance test is a Trello comment demo. The documented create operation `POST /1/cards/{id}/actions/comments` takes the comment text and no client-supplied idempotency key, so the server-assigned comment action id and date are the only definitive identity; comment text is edited with the documented `PUT /1/cards/{id}/actions/{idAction}/comments` (Trello's separate action-scoped `PUT /1/actions/{idAction}` is not used), and the 13 November 2026 connector migration observed that such an edit preserves the original creation time and adds a last-edited time, which read-back must distinguish from a second write. Comments are read back through `GET /1/cards/{id}?actions=comments` under bounded pagination. Upstream limits are 300 requests per 10 s per API key and 100 per 10 s per token with HTTP 429 on excess; the outbox must not turn a 429 into a retry storm. Trello markdown normalisation (including strikethrough) and live connector pagination, dropped-response, duplicate and actor behaviour remain **NOT RUN**; the migration's byte-identical comment read-back is evidence about that migration, not a marker-protocol qualification. [disposition #26; D42; L7, L8, L9]

Parse foreign/malformed markers as untrusted observations only. Expected own marker is confirmed only against the durable outbox/mapping/known author identity. A forged heading/key cannot recreate approvals, leases or state. Marker parsing supports read-back/discrepancy reporting; SQLite is never reconstructed from Trello comments. Owner edits remain scope proposals against the authoritative approved revision; Chief does not overwrite them.

Tests: Markdown normalization/fence repair; duplicate key; changed digest; forged author/board; pagination/truncation; crash before/after send/read-back; unknown create outcome; edit-versus-new-write discrimination; reversed sequence; stale remote status; description-taxonomy (component identifiers included) or acceptance-checklist state divergence, or a migrated checklist altered or removed, on read-back; HTTP 429 handling; bound board/card/comment id survives a renamed board, a list rename or a card move. ## 14. Goal anchor and drift predicates — VES-22 / §18 item 14

Traceability: §6 cross-cutting, §9, §12; D31, D33. Choice: stable goal/criterion IDs, canonical anchor hashes including text/checks/constraints, explicit Planner-authored typed edges, durable re-derivation. No LLM prose-based coverage inference.

### Enabling-path validation

For each anchored task, active attempt, lease, dispatch, review, check and merge, `object_criteria` must identify the same goal, the current admissible anchor and a valid criterion. `PreAnchorDiscovery` instead requires the intake-bound admission of §1 and forbids fabricated criterion edges. An enabling edge is valid only if a **bounded visited-set traversal** of same-goal dependency edges reaches a direct task-to-criterion edge under the same anchor. The traversal rejects: a cycle; a missing node; a wrong goal/anchor; a withdrawn terminal path; and a path that reaches no direct criterion. It persists the edge/source revisions used, and task-edge/anchor/criterion/withdrawal changes invalidate downstream admissions and certificates in the same writer transaction. Paths are recomputed from durable rows, not from the plan tree. The orphan/blind-spot enumeration below is task-scoped SQL and is **incomplete on its own**: the audit must enumerate missing/mismatched edges for ALL active object types, not only tasks. Coverage is not acceptance — an enabled path does not mean its check passed; goal acceptance still requires the original root obligations and actual integrated exact-SHA proofs. Contradictory amendments go to Owner change control, never silently replacing the root. Fixtures (target, NOT RUN): object-only orphans, broken/cyclic enabling paths, withdrawal, concurrent invalidation and pre-anchor cases. [disposition #30]

### Orphan work

For current anchor membership, open tasks are those not terminal (`integrated_closed|withdrawn|cancelled`); verified handoffs and blocked/recovery-held work remain open and visible. A task with no valid criterion edge is orphan work and cannot dispatch. Inflight attempts also require matching object edges/fence; the integrity audit checks them independently rather than relying on the original task row.

```sql
SELECT t.task_id
FROM tasks AS t
WHERE t.goal_id = :goal_id
  AND t.state NOT IN ('integrated_closed', 'withdrawn', 'cancelled')
  AND NOT EXISTS (
    SELECT 1
    FROM task_criteria AS e
    JOIN anchor_criteria AS c
      ON c.anchor_id = e.anchor_id AND c.criterion_id = e.criterion_id
    WHERE e.task_id = t.task_id
      AND e.anchor_id = :anchor_id
  );
```

### Blind spots

A current criterion without valid PASS and without open covering work is a blind spot. NOT RUN is **not PASS**, even with a genuine reason. PASS must match current criterion/check/SHA/environment and intact evidence; `valid` is maintained/invalidation-audited from those bindings, not trusted merely because a worker set it. Enabling edges count only after the path validator accepted them.

```sql
SELECT c.criterion_id
FROM anchor_criteria AS c
WHERE c.anchor_id = :anchor_id
  AND NOT EXISTS (
    SELECT 1 FROM check_results AS r
    WHERE r.goal_id = :goal_id
      AND r.anchor_id = c.anchor_id
      AND r.criterion_id = c.criterion_id
      AND r.check_digest = c.check_digest
      AND r.status = 'PASS' AND r.valid = 1
  )
  AND NOT EXISTS (
    SELECT 1 FROM task_criteria AS e
    JOIN tasks AS t ON t.task_id = e.task_id
    WHERE e.anchor_id = c.anchor_id
      AND e.criterion_id = c.criterion_id
      AND t.goal_id = :goal_id
      AND t.state NOT IN ('integrated_closed', 'withdrawn', 'cancelled')
  );
```

These are precise predicates against the designed schema, **not tested production SQL**. DB integrity/path validity are prerequisites; foreign-key corruption is not “no drift”. Run them before every AnchoredInvocation dispatch transaction, on scope/check/proof changes, at proposed five-minute R9 cadence, on restart of anchored goals and before acceptance. PreAnchorDiscovery uses the intake/scratch validation in §1; absent pre-Gate-1 anchors are neither synthetic PASS nor anchor-based drift findings. Findings use stable attention keys. The audit reports and parks orphan work; it does not silently revise the anchor/plan to hide findings. Only explicit new covering work or a valid current PASS resolves a blind spot.

Before raising acceptance and again before recording Owner acceptance, every issue in the approved plan must be `integrated_closed` with independently valid attached proofs and confirmed remote closure; planned blocked/recovery-held/verified-handoff/withdrawn/cancelled work cannot satisfy that guard, even if another task has a valid PASS for the same criterion. Every root criterion must also PASS independently, with zero open orphan work and no unresolved blind spot. Under D36 this guard is baseline law: planned work still in `verified_handoff` or awaiting merge cannot satisfy planned-issue closure. Test a traced blocked planned task plus a valid criterion PASS: drift may be clear, but acceptance must fail. UI at 50 issues uses searchable criterion-to-work table/grouping, direct/enabling labels, per-criterion status and dedicated orphan/blind-spot filters, not an unreadable all-node canvas.

Mandatory faults: inject zero-edge task (no dispatch); remove sole coverage (immediate blind spot); wrong anchor/criterion scope; fake enabling path/cycle; stale PASS/new SHA; NOT RUN with real reason remains unresolved; third amendment after restart parks; amended check cannot reuse old PASS; acceptance rejection keeps same anchor/goal budget.
